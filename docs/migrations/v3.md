# Migrating to v3

Version 3 formalized the shared theme, density, provider, and package-export contracts while preserving the minimum compatibility needed for existing consumers.

This document is historical migration guidance. New code should follow the current README and Storybook examples rather than adopting compatibility paths described here.

## Stylesheet entry point

Existing consumers can continue importing the aggregate stylesheet:

```ts
import "@mivama/ui/styles.css"
```

That entry point remains canonical in v3. Advanced consumers may use `tokens.css` and `themes.css` explicitly when they own the rest of their component-style integration.

## Theme and density

New and migrated application shells should use `MivamaProvider`:

```tsx
<MivamaProvider theme="portal" density="compact">
  ...
</MivamaProvider>
```

The equivalent DOM attributes are `data-mivama-theme` and `data-density`.

Portal applications that previously relied on denser defaults should use `density="compact"`. Coarse-pointer contexts still retain the package's maintained touch-target sizing.

## Editorial theme compatibility

`.mivama-editorial-theme` remains supported in v3 only as a compatibility alias for existing consumers. Migrate to `theme="editorial"` or `data-mivama-theme="editorial"` before v4.

Removal is tracked in issue #59. No replacement class alias is planned.

## Provider-less portal compatibility

Existing v3 consumers that render Dialog, Sheet, or Tooltip without `MivamaProvider` still receive a compatibility fallback that copies theme/density shell attributes to matching portaled content.

New code should not depend on that DOM-query/MutationObserver path. Wrap the application shell in `MivamaProvider` so the provider owns the portal container and theme/density context directly.

Removal of the provider-less fallback is tracked in issue #60 for v4.

## Fonts

v3 did not add another typeface. The vendored Onest files remain the packaged font source.

## Removal policy

Compatibility paths that survived the v3 migration are not permanent architecture. They have explicit major-version removal issues and should not gain new responsibilities, examples, or parallel abstractions.
